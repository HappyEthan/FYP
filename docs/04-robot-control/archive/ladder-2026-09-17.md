# 磁触觉 Z 标定梯子实验：历史方案

日期：2026-09-17。依据：本会话用户逐项确认，以及 `recordings/` 中 31 条历史记录的离线复核。

本文保存 2026-09-17 的旧梯子设计，不是当前批次的操作或批准规则。旧文要求逐拍实际位姿、双向梯子及固定示例档位；当前阶段改用命令 TCP Z 与 `|ΔBxy|` 建立对应关系，具体档位随毛笔和装配变化。**平台侧功能当时仅通过离线测试，未由本文证明真机性能**；文中数值均为当时条件下的候选值，不构成当前安全结论。

## 目标与产物

产出一张可被 `validate_calibration()` 接受的前馈表，把 StrokePlan 的 `g_target` 映射为 `z_ff`：

```json
{
  "version": 1,
  "feature": "dBxy_norm_uT",
  "source": "measured",
  "installation_id": "<现场填写>",
  "sensor_mount_id": "<现场填写>",
  "filter": "<现场填写>",
  "speed_range_mm_s": [10, 10],
  "directions": ["+x"],
  "depth_mm": [0, 2.857, 5.714, 8.571, 11.429, 14.286, 17.143, 20.0],
  "amplitude_uT": ["<由实测填入>"],
  "approved": true
}
```

一次实验运行（一个 run 目录）应能独立产出上述 `depth_mm` / `amplitude_uT` 对。`approved` 必须由人工审核后置位，程序不得自动置真。

## 现状与问题

实验平台 `src/brushbot/experiments/` 已具备本任务所需的绝大部分结构：

- `sensor.csv` 每个磁样本带主机单调时钟 `host_rx_ns`（`recording.py:21`）。
- `control.jsonl` 每拍一行，带 `sample_seq`、`depth_ff_m`、`depth_fb_m`、`z_cmd_m`（`engine.py:228`）。
- `summarize_scan()` 已能按 `sample_seq` 把两侧 join 成 `(depth_mm, amplitude_uT)` 对（`calibration.py:85`）。
- 采集特征全链路使用 `hypot(dBx, dBy)`：`calibration.py:100`、`engine.py:210`、`acquisition.py:201`。`dBz` 不参与分析，但原始三轴逐样本保留。

存在三个缺口：

1. **实际位姿从未被记录。** `engine.py:241` 把 `"actual_pose_available": False` 和 `"actual_pose_m_rad": None` 硬编码。因此 `summarize_scan()` 只能退化为 `position_basis: command_based`，用 `depth_ff + depth_fb` 当深度——是指令深度，不是实际深度。
2. **平台没有适配本实验的路径形态。** `validate_experiment()` 只接受 `path.kind` 为 `line` 或 `circle`（`config.py:106`），且 Z 由 `z.start_tcp_z_mm` / `z.end_tcp_z_mm` 线性插值（`trajectory.py:147`）。两者都无法表达"多趟往复、逐趟定深"。
3. **`summarize_scan()` 只认 `phase == "cruise"`**（`calibration.py:111`），无法表达梯子各档的测量段。

## 离线复核结论（决策依据）

以下结论来自 `recordings/` 中 31 条历史记录的离线分析，用于校正设计假设。**这些记录没有运动日志，无法确认当时的实际动作**，因此结论只作为量级判断，不作为验收依据。

### 当时对漂移的初步判断（现已撤回）

按 ΔBxy 逐条线性拟合：

| 记录 | 时长 | ΔBxy 斜率 | 首 10 s → 末 10 s | 全程变化 |
|---|---|---|---|---|
| `2026-09-12_17-30-24_496830` | 285 s | +0.017 μT/s | 20.4 → 24.4 | **+4.8 μT** |
| `2026-09-12_17-25-14_492390` | 85 s | −0.001 μT/s | 9.9 → 10.0 | −0.1 μT |
| `2026-09-12_15-28-41_569245` | 225 s | +0.056 μT/s | 30.9 → 23.0 | +12.5 μT |

最长的一条 285 s 记录中 ΔBxy 全程只变化 4.8 μT。**按九分钟（540 s）外推，漂移贡献约 9 μT。**

当时认为不分析 `dBz` 即可忽略其漂移；这个推断现已撤回。偏置也可能影响 X/Y；用户观察到旋转笔头后 XY 磁读数明显改变。上述历史记录没有运动日志，不能排除姿态、装配或基线因素，也不能据此断言当前实验不受漂移影响。

### 接触质量才是主要风险

按 ΔBxy 的 p95 分组，界线清晰，中间没有过渡带：

| 分组 | 记录 | ΔBxy p95 |
|---|---|---|
| 真实下压 | `2026-09-12_16-29-38_178073` 等 6 条 | 258–462 μT |
| 未接触/静止 | `2026-09-12_17-30-24_496830` 等 4 条 | 18–39 μT |

用户判据：真实下压时 ΔBxy 必定超过 200 μT。

**而 `2026-09-14` 的三条记录（`09-19-51` / `09-23-56` / `09-45-34`，各约 117 s）p95 仅为 84 / 94 / 119 μT**，落在两个分组之间。按上述判据，这三条并未建立真实接触。这与"接触间歇"的既有怀疑一致。

因此本设计的主要风险是**接触质量**，不是漂移。

| # | 决策 | 取值 |

| 1 | 实现落点 | 补齐 `src/brushbot/experiments/`，不新建并行实现 |

## 设计

### 数据链路：记录实际位姿

唯一改动点是 `engine._run_step()`（`engine.py:228` 起）写入 `control` 行的那一处。

现状：

```python
"actual_pose_available": False, "actual_pose_m_rad": None,
```

改为每拍调用一次 `self.arm.read_state()`，写入：

- `actual_pose_available`: `True`
- `actual_pose_m_rad`: `state["tcp_pose"]`（米/弧度，六元组）
- `actual_rx_ns`: `state["request_end_ns"]`（主机单调时钟）

三条约束：

1. **读失败不中止。** 整个读取包在 `try/except` 中；失败时该拍写回 `False` / `None` / `None`。一次网络抖动不应终止整轮扫描。
2. **共用主机时钟。** `read_state()` 返回的 `request_end_ns` 来自 `adapter.py:104` 的 `clock_ns()`，与 `sensor.csv` 的 `host_rx_ns` 同源，因此两侧可直接对齐。
3. **耗时必须先实测。** 这是每拍新增一次 `HRIF_ReadActTcpPos` 网络往返。若单次耗时使单拍超过 `max_tick_lateness_s`，运行会被 `deadline_miss` 中止。超预算时退化为每 N 拍读取一次，并在行中记录 `actual_pose_stale_ticks`。

### 梯形路径

`configs/experiments/` 新增一种 path kind。示例：

```json
{
  "version": 1,
  "name": "z_ladder_x",
  "path": {
    "kind": "ladder",
    "axis": "+x",
    "travel_mm": 100,
    "depth_from_mm": 0,
    "depth_to_mm": 20,
    "steps": 8,
    "order": "down_then_up",
    "transit_z_mm": 50
  },
  "motion": {"speed_mm_s": 10, "accel_mm_s2": null},
  "control": {"enabled": false}
}
```

`kind == "ladder"` 时 **`z` 块禁用**——梯子自带 Z 调度，`start_tcp_z_mm` / `end_tcp_z_mm` 无意义。`validate_experiment()` 需相应调整顶层必填字段。

档位由 `contact_z_mm` 推算：`tcp_z_i = contact_z_mm − depth_i`。绝对高度只在预览中显示，不写入 JSON，以保证 `contact_z_mm` 只有 installation 一个来源。

`order: "down_then_up"` 的档序为 `0→20` 再 `20→0`，共 **16 趟**；每个档位恰好被访问两次。

每趟编译为 4 段，相位名带两位序号：

| 段 | 动作 | 相位名 |
|---|---|---|
| 1 | 起点由 `transit_z_mm` 降至 `contact_z_mm − depth_i` | `approach_<i>` |
| 2 | 恒深，沿 `+x` 匀速走 `travel_mm` | `measure_<i>` |
| 3 | 终点抬升至 `transit_z_mm` | `lift_<i>` |
| 4 | 在 `transit_z_mm` 沿 `−x` 返回起点 | `transit_<i>` |

第 4 段保持录制，用于对照"移动 vs 静止"的磁信号。

各段速度来源：

| 段 | 速度来源 |
|---|---|
| `approach` / `lift` | `setup["approach_speed_mm_s"]`（慢速解粘） |
| `measure` | `spec["motion"]["speed_mm_s"]` |
| `transit` | `setup["return_speed_mm_s"]` |

`measure` 段速度受 `setup["max_xy_speed_mm_s"]` 约束；`approach` / `lift` 段的 Z 速度受 `setup["max_z_speed_mm_s"]` 约束。

### 分析产物

新增 `summarize_ladder(run_dir)`，**不改动现有 `summarize_scan()`**（闭环实验仍在使用）。

输出结构：

```json
{
  "run_id": "...", "feature": "dBxy_norm_uT", "source": "measured",
  "position_basis": "actual_pose", "approved": false,
  "rungs": [
    {"index": 0, "depth_cmd_mm": 0.0, "depth_actual_median_mm": 0.02,
     "amplitude_down_uT": 61.3, "amplitude_up_uT": 68.9,
     "amplitude_uT": 65.1, "n": 742, "hysteresis_uT": 7.6}
  ],
  "drift": {"total_uT": 0.0, "per_minute_uT": 0.0}
}
```

`amplitude_uT` 取 `amplitude_down_uT` 与 `amplitude_up_uT` 的均值，写入最终标定表的就是这个值。两者之差记为 `hysteresis_uT`，用于 E3 迟滞观测。

`depth_actual_median_mm` 由实际位姿算出（`contact_z_mm − actual_z`），与 `depth_cmd_mm` 的偏离量反映指令与实际的差。若实际位姿不可用，则该字段为 `null`，并回退到 `depth_ff_m + depth_fb_m`，同时把 `position_basis` 标为 `command_based`——**这种输出不得用于生成 `approved` 表**。

`approved` 保持 `false`，必须人工审核后固化成表。

### 接触质量判据

不使用固定阈值（浅档幅值本就低）。改用两条结构性检查：

1. **单调性**：各档 `amplitude_uT` 必须严格递增。任一档低于前一档，即判定该档未建立真实接触，标记为不合格。
2. **原点检查**：第 0 档（`depth_mm` = 0）的幅值应接近静止底噪（实测量级 20–39 μT）。明显偏高说明 `contact_z_mm` 标低，整条曲线不可用。

这两条同时是 `validate_calibration()` 中 `amplitude_uT` 严格递增要求的前置，使失败发生得更早、原因更明确。

## 安全边界

编译期检查（`trajectory.py`）逐条对应：

| 检查 | 位置 | 梯子需满足 |
|---|---|---|
| 工作空间 | `:92` | 含 transit 段 Z = 50 mm；需落在 `workspace_min/max_mm` 内 |
| 单拍步长 | `:170` | transit 100 mm @ 30 mm/s → 0.6 mm/拍，需 `max_step_mm ≥ 0.6` |
| Z 速度 | `:155` | approach 最大 30 mm @ 2 mm/s，需 `max_z_speed_mm_s ≥ 2` |
| 压深 | `:151` | 最深 20 mm；`max_depth_mm ≥ 20`；`depth_mm` 不得为负 |

运行期 `_check_pose()`（`engine.py:183`）每拍复查工作空间与步长。

`depth_mm` 必须 ≥ 0（`trajectory.py:151` 拒绝负值），因此任何高于 `contact_z_mm` 的运动只能作为 `transit` 段，不得作为 `measure` 段。

## 前置条件：installation 配置

`validate_installation(hardware=True)` 要求约 30 个字段全部非空且 `verified: true`。这是本实验的硬前置。

**已有实测值的候选**（仍需现场复核，不得直接沿用）：`origin_x/y_mm` = (−300, 500)、`wait_z_mm` = 130、`contact_z_mm` = 40、`workspace_min/max_mm` = X[−400, 100] / Y[400, 600] / Z[17, 130]。

**必须现场实测**：`installation_id`、`tcp_name`、`ucs_name`、`tool_coord_si`、`user_coord_si`、`vertical_rpy_rad`、`sensor_mount_id`、`pose_tolerance_mm`、`orientation_tolerance_rad`、基线判据四项（`baseline_window_s` / `baseline_timeout_s` / `baseline_min_samples` / `baseline_max_std_uT` / `baseline_max_drift_uT_s`）、`sensor_max_age_s`、`max_tick_lateness_s`、`stop_timeout_s`、夹爪三项、`filter`。

`contact_z_mm` 尤其关键：梯子第 0 档就是这一高度，它是整条曲线的原点。历史脚本使用 `START_Z = 36`、`ENTRY_Z = 30`，与 40 不一致，**必须实测确认，不得沿用历史数字**。

需按 `2026-09-09-experiment-platform-operations.md` 的模板生成带逐字段来源说明的空白 JSON。

## 测试（全部可离线运行）

1. **ladder 编译**：档数与相位名、往返顺序、`depth_mm` 序列；步长 / 工作空间 / 压深越界必须被拒绝。
2. **位姿记录**：假臂返回已知位姿 → `control.jsonl` 中 `actual_pose` 正确；假臂抛异常 → 该拍写 `False` / `None` 且**不中止**。
3. **`summarize_ladder`**：合成 run 目录 → 各档幅值、升降迟滞、漂移估计正确；非单调输入被标记不合格。
4. **端到端**：假设备 + 合成磁信号跑完整个梯子 → 产出可审核的 `rungs`。

## 上机前必须完成的测量

1. **`HRIF_ReadActTcpPos` 单次耗时。** 决定每拍读位姿是否顶破 `max_tick_lateness_s`；超预算则退化为每 N 拍一次。
2. **`contact_z_mm` 实测。** 梯子原点，必须独立确认。
3. **installation 全部字段实测并置 `verified: true`。**

## 未决与风险

- **本方案未在真机运行过。** 实验平台此前只有假设备与合成信号测试；梯子编译、位姿记录与 `summarize_ladder` 已有离线测试覆盖。
- **接触质量是主要风险。** 若 09-14 的"没压上"是系统性的，梯子同样会失败；单调性判据会让它失败得明确，但不解决成因。
- **`dBz` 漂移成因未确认。** 本实验不分析 `dBz`，故不影响结论；但若该漂移实为传感器偏置，则同样影响 `dBx` / `dBy`，需要重新评估。
- **单方向适用性。** 产出的表 `directions: ["+x"]` 只对 `+x` 有效。其他方向需要各自的梯子运行。
- **引擎节拍判据曾误杀整轮扫描（已修，留痕）。** 引擎用"计划索引不得跨拍前进"判循环是否掉队，
  但时间轴的采样时刻与引擎 `elapsed` 各自带浮点误差、两个网格对不齐，某一拍会合法地跨过 2 个样本。
  出厂梯子配置实测误判 228 次，真机上会在约 7 秒时中止。单段轨迹（直线/圆）因游离尾样本恰在时间轴
  末尾而被末索引夹住，看不出问题。已改为按"计划时间推进量"判定并容忍 2 个样本。这类"编译期时间轴"
  与"运行期节拍"的耦合很微妙，改动任一侧都需要端到端夹具复验。
